Database Foundation: Why It Matters

The secure foundation where all business and user data lives - built with healthcare-grade security from day one.

Multi-Tenant Security

Every piece of data is automatically isolated by clinic - clinics can never see each other's data, even by accident

Production-Ready Schema

Core tables for tenants, customers, and users deployed with full security isolation

Type-Safe Queries

Database code checks itself automatically - catches bugs before they reach production

Migration System

Database changes are version-controlled and can be deployed safely without downtime

Row-Level Security (RLS)

The database itself enforces data isolation - not application code. This means:

  • Impossible to accidentally leak data between clinics
  • Security enforced at the lowest level - even if application code has bugs
  • Healthcare-grade compliance - meets strictest data protection requirements
  • Proven with automated tests - cross-tenant access is blocked at database level

This architecture is designed for healthcare data - where security isn't optional, it's essential

Why No Self-Registration?

For MVP, only admin-invited users can access the system. This ensures proper business setup, prevents spam accounts, and maintains data quality. We can add self-registration later when we have payment integration and automated onboarding flows.

Key Decisions

Questions Refactor

Before: Embedded JSONB in templates
After: Dedicated table with full RLS
Benefit: Better querying, security, flexibility

RLS Pattern

Tenant isolation: Via app.tenant_id session variable
User ownership: Service-layer checks (not RLS)
Reason: RLS enforces tenant, app enforces user

Dynamic Routing

Pattern: Regex-based route matching
Parameters: Extracted from URL paths
Example: /assessments/:id/progress

All migrations deployed: Questions table refactored with full backward compatibility

Job Queue Infrastructure

A database-driven polling queue for background processing - no external dependencies like SQS.

Database-Driven Design

Jobs stored in PostgreSQL with full transactional guarantees. No external queue service required - simpler architecture, lower cost.

Atomic Job Claiming

Uses FOR UPDATE SKIP LOCKED for concurrent worker safety. Multiple workers can poll without conflicts.

Exponential Backoff

Failed jobs retry with increasing delays. Configurable max attempts prevent infinite loops on permanent failures.

EventBridge Integration

Scheduled processing via AWS EventBridge Cron. Serverless polling at configurable intervals (e.g., every minute).

Job Lifecycle

1. Enqueue

Job created with type, payload, and scheduled time

2. Claim

Worker atomically claims pending job with SKIP LOCKED

3. Process

Handler executes job logic (e.g., scoring)

4. Complete

Job marked complete or scheduled for retry

Why Not SQS?

Database-driven queue means one less AWS service to manage, full transactional consistency with assessment data, and simpler local development. SQS can be added later if scale requires it.

Assessment APIs & State Machine

Complete API endpoints for the assessment lifecycle with robust state management.

API Endpoints Built

POST /assessments/start

Create or resume: Returns existing in-progress or creates new
Validation: Template exists, user authorised

PUT /assessments/:id/progress

Save answers: Stores responses as user navigates
Step tracking: Updates current step position

POST /assessments/:id/submit

Validate complete: All required questions answered
Enqueue scoring: Creates job for background processing

State Machine

Assessment States

not_started → in_progress → submitted → scored → completed

+ abandoned: For incomplete assessments after timeout

Transition Rules

Only forward: Cannot go back to previous states
Service enforced: Validation before each transition
Audit ready: State changes logged with timestamps

Ownership Checks

Pattern: RLS isolates tenant, service validates user
Reason: Multiple users per tenant need separation

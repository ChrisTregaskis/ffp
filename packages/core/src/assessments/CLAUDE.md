# Assessment domain (`@ffp/core`)

Local map for the assessment domain. High-level engine design: `project-documentation/assessment-engine.md`. Standards: the `backend` and `database` skills, and `.claude/rules/rls.md`. Read this before editing here, and update it when the domain's structure or contracts change.

## What this domain is

Two distinct halves living side by side:

1. **User-facing lifecycle** (per-member, RLS-enforced) — starting/resuming an assessment, saving progress with branching, submitting, scoring, results.
2. **System catalogue** (cross-organisation, RLS-excluded) — the flows, steps, templates and question bank that define _what_ an assessment is. Authored by system admins.

The wider domain spans three packages: business logic here (`@ffp/core`), handlers in `packages/functions/src/assessments/` (+ admin handlers in `packages/functions/src/admin/`), and the UI in `packages/web` (`components/assessment/`, `hooks/assessments/`, `contexts/assessments/`, consumer pages under `pages/protected/programme-user/`).

## Data model (catalogue)

```
assessment_flows (scoring_config: jsonb, is_active)
  └─ flow_steps (order, type, config: jsonb, next_step_rules: jsonb, default_next_step_id)
       └─ assessment_templates (version auto-increments)   ← optional per step (templateId)
            └─ template_questions (display_order, config_overrides)
                 └─ questions (slug, type, options: jsonb, validation: jsonb, score_dimension)
```

- `scoring_config` is **flow-level jsonb** (`dimensions[]` + `programmeMappings[]`), not per template. A question's score comes from `QuestionOption.score`.
- **Score dimensions** (`SCORE_DIMENSIONS`, the pg enum `score_dimension`): `activity`, `age`, `strength`, `mobility`, `balance`. `@ffp/database` is the one source; core's `scoreDimensionSchema` derives from it.
- Branching lives in `flow_steps.next_step_rules` (`NextStepRule[]`: priority → conditions → action). Actions: `goto_step`, `show_warning`, `end_assessment`. Linear fallback is `default_next_step_id`.
- Schemas: `packages/database/src/schema/{assessment-flows,flow-steps,assessment-templates,template-questions,questions}.ts`. Types/constants under `packages/database/src/{types,constants}/`.

## Local contracts

- **RLS:** user-layer tables (`user_assessments`, `user_assessment_answers`, `assessment_safety_triggers`) are RLS-enforced — always set context in a transaction (see `.claude/rules/rls.md`). Catalogue tables (flows, steps, templates, template_questions, questions) are **RLS-excluded by design**; protect every catalogue endpoint — **reads as well as writes** — with the `system_admin` gate, not RLS: wrap the handler in `withSystemAdmin` (`src/lib/system-admin-gate.ts`) inside `withErrorHandling`, which also logs every refusal. `/admin/` means system admin only; the member-facing reads of the same catalogue go through `packages/functions/src/assessments/`, which is ungated by design.
- **Member answers are validated on the server, on save and on submit.** Each answer is checked against its question's **effective** validation (`configOverrides.validation ?? validation`, `resolveEffectiveValidation`) by `validateAnswer` in `schemas/question-answer.schema.ts`, which is browser-safe so the member UI can share it: type per question type, option membership, `maxSelections`, min/max (value, text length, video-response result; a scale defaults to `DEFAULT_SCALE_RANGE`), and `required`, where `[]`, `''` and whitespace are no answer. An answer to a question outside the assessment's flow is a 400, not a foreign-key 500. **Only what a request changes is checked:** the member's client resends every answer it holds, so an answer sent back exactly as stored is neither re-checked nor rewritten (`findChangedAnswers`); otherwise one answer gone stale under a catalogue edit (its question unassigned, its rules tightened) would block every save and Back. **A blank answer on save clears the stored one** (the row is deleted), even for a required question, so a member can empty an answer and still move back; required is enforced at submit, and the member UI blocks Continue on it. Submit checks every stored answer still in the flow plus the changed ones, and requires each required question on a template the member reached, scoped to the flow's own templates. A template counts as reached when it holds a real (non-blank) answer to a question no other template in the flow shows: an answer to a shared question cannot say which step it was given on. `pattern` is not enforced. A failure is a `ValidationError` whose `details` is `[{ path: 'answers.<questionId>', code, message }]` (`ApiFieldError`, `schemas/api-error.schema.ts`), the same shape a request body that fails to parse reports, with a member-facing message. A **deactivated** question still assigned to a template is still shown to members, so its answers are accepted and checked but it is never required.
- **Member-facing lifecycle functions check ownership.** RLS isolates organisations, not members, so `saveProgress`, `submitAssessment`, `getAssessmentResults` and `acknowledgeSafetyAdvice` refuse another member's assessment as a 404 (`findOwnAssessment`), and `startAssessment` / `getUserAssessmentStatus` only ever read by the caller's own user ID.
- **A save moves the stored step on only when it advances.** `saveProgress` stores `currentStep` as sent, and moves it to the step branching picks only when the request sets `advance` (the member's step-level Continue). The client saves in the background as the member moves between questions inside a step, so a save that always advanced would resume them past the questions still to come. `startAssessment` clamps a resumed unsubmitted assessment with the same rule (`toResumableStep`), so a stored position past the last question step (results) resumes on that step. The rule (and the client's `isLastSubmittableStep`) assumes every member's path runs through the flow's last question step by order: branching must not jump from an earlier question step straight to results, or the member is put back on a step they skipped.
- **Members never receive `riskLevel` or `recommendedTemplateSlug`.** The results handler parses through `assessmentResultsResponseSchema`, whose `memberAssessmentScoresSchema` omits both; the stored scores and the admin dry-run keep them.
- **A `seek_medical` warning gates the member's result.** `submitAssessment` runs the flow's rules over the full answer set (`findSafetyTrigger`), because the safety question is on the last step and a submit is not a save, and records one `assessment_safety_triggers` row per assessment (unique on the assessment; the options the rule names, so a "none" ticked alongside is left out). The results and resume responses carry `safetyGate`; `acknowledgeSafetyAdvice` sets `safety_acknowledged_at` once, owner-checked, and refuses an assessment with no trigger. It gates what the member sees, not programme generation. `saveProgress` still appends to `warnings_shown`, which is a save-time audit trail that repeats on every re-trigger, so it is never the count. Other warning types are not shown anywhere yet.
- **Scoring and branching are pure functions** — no side effects, no DB. Keep them that way; they're reusable for preview/dry-run. Persisting belongs in services/repositories.
- **Extend, don't fork:** new catalogue admin work should mirror the template-CRUD layering here (schema → repository → service → handler) and, on the web side, the programme-template patterns (`SessionCard`, `swapAdjacentItem`, mutation hooks) together with the shared UI those screens draw on (`InlineFormPanel` in `components/molecules/`, `DeleteConfirmModal` (on `ConfirmModal`) in `components/organisms/`, `reorderableItemActions` in `utils/`).
- **A parent and its children get a service each:** `flow.service.ts` / `flow-step.service.ts` and `template.service.ts` / `template-question.service.ts`. The parent service never imports the child. Templates have one publicId resolver, `resolveTemplate` in `template.service.ts`, which the child imports; `resolveFlow` still lives in the step service.
- **Wellness positioning:** prefer wellness-neutral language in new copy; avoid introducing clinical/medical framing. The `seek_medical` warning type is the one that holds the member's result for their consent; its name predates the positioning, so keep the member-facing copy it carries as advice to speak to a health professional, never a diagnosis.

## Gotchas

- **The admin flow list is paginated and carries a step count.** `GET /admin/assessment-flows` takes `page`, `pageSize`, `sortBy`, `sortDirection`, `search` (name + description) and `isActive`, and returns `{ data, pagination }` built from the shared `applyPagination` / `escapeLikePattern` / `buildPaginationMeta` helpers. `stepCount` comes from a left join restricted to active steps, so a soft-deleted step does not inflate it. It defaults its sort to `name` and breaks ties on `id`.
- **The admin template list is paginated the same way** (`search` over name and description, `isActive`), defaulting to `name` with an `id` tie-break, and each row carries `questionCount` and `flowCount` (flows with an active step linking it), grouped in subqueries so the two joins cannot multiply. The web's whole-catalogue readers (the step's template picker, the template name map) page through it rather than calling a second unpaginated query. **The admin template routes resolve by `publicId`**; `GET /admin/assessment-templates/:publicId` returns the row, its questions as stored (`templateQuestionResponseSchema`, untransformed) and `flows`. The member's `GET /assessments/templates/:id` reads the same template by the UUID its flow step carries — `getTemplateService` keeps that key.
- **A flow's `description` clears on an explicit `null`** and survives omission, mirroring the question update contract. Nothing else on the flow update shape is nullable.
- `flow_steps.order` is **not unique** per flow (parallel branches share a value) — reorder logic must account for that; it's not a `sort_order` swap like programme templates.
- **Step updates are validated against the merged row, not the payload**, the same way question updates are. `updateStepService` applies the template clean-up, then checks the type and link the row _will_ carry: only `questions` and `video-assessment` link a template, and an update leaving either of them without one is refused with a 400. So `templateId` clears on an explicit `null` and survives omission, but a `null` sent against a step that still renders a template is rejected rather than stranding a member on a step with no questions. The clean-up fires on **any** update that resends a non-linking type, not only a type change, so a save self-heals a stale `template_id` left by the old contract; a `templateId` the payload sends explicitly still wins over it. `createStepService` runs the same merged check over the payload, so a `questions` or `video-assessment` step cannot be created without a template. Create does not drop a link, though: a direct API call can still store a `templateId` on a step type that takes none (the web form strips it before sending).
- **The flow detail read serves both admin surfaces.** `GET /admin/assessment-flows/:publicId` returns metadata plus the ordered active steps, each carrying `branchingRuleCount`; `assessmentFlowWithStepsSchema` in `schemas/assessment-flow.schema.ts` is the browser-side parse contract for it, so the metadata form and the step builder share one query and one cache entry.
- **Reorder refuses on a branching flow with a 409**, and both seeded flows carry rules (the wellness flow's safety warning, the demo's `goto_step`) — so reorder rejects both. `flowHasBranching` is the server's rule; the web builder keeps its own copy (`packages/web/src/utils/flow-branching.ts`) to disable the controls up front, with the server staying authoritative.
- `template_questions` is the mirror image: **`UNIQUE(template_id, display_order)` is enforced**, so a reorder cannot write final positions directly. `reorderTemplateQuestions` parks every row on a temporary negative order first, then writes the positives (the same idiom as `programme-templates/template-session.repository.ts`). Don't copy the flow-step reorder here, or the other way round.
- **Question updates are validated against the merged row, not the payload.** `updateQuestionService` loads the stored question, applies the type-change clean-up, then runs `questionShapeSchema` over the result — so a partial cannot reach a state a create would be refused. `description`, `videoId`, `scoreDimension` and `validation` clear on an explicit `null` and survive omission; nothing else on the update shape is nullable. A supplied `validation` replaces the stored one whole — it is a value object, so a partial one drops the sub-fields it omits. Do not put a Zod `.default()` on the shared write base: `.partial()` keeps field defaults, and that is how an omitted `isActive` once reactivated soft-deleted questions.
- **The admin question list is paginated like the flow list** (`page`, `pageSize`, `sortBy`, `sortDirection`, `search` over text and slug, `type`, `isActive`), but defaults its sort to `questionText` and breaks ties on `id`, so it pages stably without a caller-supplied sort. Get, create and update all return `{ question }` shaped by `adminQuestionDetailSchema` — the row plus `usage` (template assignments, and flows whose `scoring_config` names it, matched in jsonpath) and `linkedVideo`.
- **A question's `videoId` has no foreign key**, so the service checks it instead: a newly set `videoId` must be an `active` video. A stored link is not re-checked on an unrelated edit, so a stale one does not lock the question; it reads back as `linkedVideo: null`.
- A unique-constraint violation that escapes a service's own guard is translated centrally in `lib/database-errors.ts` (called from `lib/lambda-wrapper.ts`), so a lost race answers 409 rather than 500. Domains do not need their own driver-error handling. The constraint name goes to the log, never to the caller. **Only `23505` is mapped** — every other SQLSTATE still reaches the 500 branch. A foreign-key violation (`23503`) is recognised by `isForeignKeyViolation` but mapped only where the caller knows what holds the row: the programme-template phase and session deletes turn it into a 409.
- **`video-response` questions carry a `min`/`max` duration**, which `VideoResponseQuestion` passes to `NumericQuestion` as the bounds of the result input. An earlier rule treated them as completion-only and rejected the range; it contradicted both the seed data and the renderer, and has been removed.
- `aggregate` branching condition is a **stub** (`condition-evaluator.ts` always returns false) — don't depend on it.
- **`programmeMappings[].programmeTemplateId` is a programme template slug**, not a UUID, despite the name. Scoring stores it as `recommendedTemplateSlug`, and generation resolves it with `findTemplateBySlug` (`programme_templates.slug`, unique). Editing a template's slug silently breaks every mapping that names it; nothing guards that yet.
- **Dimensions score in one of two modes.** `scoringMode: 'sum'` (the default) adds the question scores; `'modal'` takes the most frequent one, with a tie resolving to the middle of the offered option scores (`helpers/modal-scoring.ts`). Modal is for scored single-choice tallies only: any other answer still votes.
- **A dimension with nothing answered is unassessed, not scored 0.** It carries `answeredCount: 0` and no category, and is left out of the overall score, the risk level and programme matching, so any condition on it fails (`isAssessed` in `schemas/job.schema.ts`, browser-safe, so the results screen and the scoring runner share it). Scores stored before `answeredCount` existed lack it and count as assessed. The results screen hides an unassessed dimension rather than showing 0/100.
- **`affectsRiskLevel: false` keeps a dimension out of `riskLevel`** (default `true`). With no eligible dimension the risk level is omitted, which the stored scores and the results screen already treat as optional. The overall risk grades the lowest eligible score against the global 70/40 thresholds, not a dimension's own `riskThresholds`.
- **Mapping `priority`: lowest first, missing last**; the first match wins.
- **The level rule lives in one place**: `LEVEL_SCORING_CONFIG` in `@ffp/database/constants` (`level-scoring.constants.ts`) — a modal `activity` tally plus an `age` bump, as six `eq` mappings onto the three level shells. The seed authors it onto the wellness flow and `tests/scoring/level-matrix.test.ts` runs every answer pattern through it. The results screen hides the `age` dimension from members. The platform organisation's `settings.defaultAssessmentFlowId` is seeded to the wellness flow, so members get it rather than an arbitrary active flow.
- No referential integrity between `scoring_config.dimensions[].questionIds` and the questions table — deleting/deactivating a question silently drops it from scoring. Validate on write if you add scoring-config editing.

## Authoring & testing

- The catalogue ships with seed data — `packages/database/seed/seed{Questions,AssessmentTemplates,AssessmentFlows,FlowSteps}.ts` (idempotent, deterministic UUIDs): the **Wellness Movement Assessment** (the primary flow, scored by the level rule) and the **Movement Check Demo** (a reduced flow kept to exercise branching and video steps). The flow seed refuses a scoring config naming a missing question or one carrying a different dimension. Changing seeded rows needs `pnpm seed:db -- --fresh`, because inserts skip existing IDs. The catalogue is also authored through the admin API under `packages/functions/src/admin/` (`assessment-flows/`, `questions/`, `templates/`). Those routes are keyed on `publicId` and gated on `system_admin`; the pre-existing programme-template routes read by `publicId` but write by UUID, and their child resources (phases, sessions, exercises) are UUID-keyed throughout. The catalogue is `publicId` on the read and on every write, so a page here passes its route parameter straight through; `.claude/rules/identifiers.md` covers where that splits elsewhere.
- Tests: `pnpm --filter=@ffp/core test`. Scoring/branching are pure and unit-test cleanly (`tests/scoring/`, `tests/branching/`); user-lifecycle tests need RLS context.
